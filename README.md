# nodepool —— 三层供给 + 一个固定出口

从 Telegram 频道和公开订阅源抓取节点、实测带宽，**合并进历史池**，对外只暴露**一个订阅地址**。
客户端里填一次，之后换节点、加源、上游全挂，都不需要你再动手。

设计思路与市场调研见 **[RESEARCH.md](RESEARCH.md)**。

## 两种用法，先选一个

| | 云端版（推荐） | 本机版 |
|---|---|---|
| 跑在哪 | GitHub Actions | 你的电脑 |
| 电脑关机 | **不影响** | 就停了 |
| 手机能用 | **能**，一个公网地址 | 不能（127.0.0.1） |
| 花钱 | 0 | 0 |
| 怎么搭 | **[SETUP.md](SETUP.md)** ← 三步 | 下面这份文档 |

**要"每天自动、手机通用"，直接用云端版。** 本机版适合调试和临时用。

```
① 自建 VPS  ─┐
② 免费额度  ─┼→  总出口(fallback)  →  手机 / 电脑 / 路由器
③ 免费池    ─┘        按 ①→②→③ 自动降级
```

降级逻辑不写在网关里，而是用客户端原生的 `fallback` 组实现 —— 客户端本来就会持续探测，
网关没必要重复做。所以网关很轻：纯标准库、无常驻子进程、不和你抢网络。

## 快速开始

```bash
cd nodepool

# 1. 装守护（网关常驻 + 每日 04:00 自动刷新）
./install.sh

# 2. 它会把订阅地址打出来，填进客户端即可
#    Clash / mihomo : http://127.0.0.1:8899/sub/clash?token=xxx
#    v2rayN / 小火箭: http://127.0.0.1:8899/sub/base64?token=xxx
```

> **`./install.sh` 要在你自己的终端里跑。** 它调 `launchctl` 注册 launchd 服务，
> 而 Agent 沙箱禁止这类操作（连 `/usr/bin/true` 的最小 plist 都会报
> `Bootstrap failed: 5`）。脚本本身已验证：plist 语法通过 `plutil -lint`，
> 网关与刷新流程都实测跑通，只差最后这步注册。

只想手工跑一次，不装守护：

```bash
./refresh.sh                 # 采集 → 测速 → 并入历史池 → 网关重载
./refresh.sh --no-collect    # 只重测已有节点（代理断线时用）
python3 gateway.py           # 前台起网关（Ctrl+C 退出）
```

> **采集需要代理，测速不需要。** 采集脚本在沙箱里跑，默认出口到不了 raw.githubusercontent / t.me，
> 默认走 `http://127.0.0.1:7897`（可用 `NODEPOOL_PROXY` 覆盖）。
> 代理不在线时 `refresh.sh` 会**跳过采集但仍然重测**，不会整轮报废。

## 目录结构

```
nodepool/
├── SETUP.md            # 云端部署三步走 ← 先用这个
├── .github/workflows/daily.yml   # GitHub Actions 定时任务(UTC 20:00)
├── ci_build.py         # 云端构建: 只筛可用性, 不测带宽
├── gateway.py          # 本机统一出口: 历史池 / 健康探测 / 订阅生成 / HTTP 服务
├── collect.py          # 采集与解析 (TG 频道 + 6 个公开源)
├── probe.py            # 用 mihomo 内核实测延迟/抖动/带宽 + 多站点复检
├── attribute.py        # 供应链溯源: 扩散广度、归属聚合、垃圾地址
├── refresh.sh          # 每日刷新: 采集 → 测速 → 并池 → 通知重载
├── install.sh          # launchd 安装/卸载/状态/立即刷新
├── run.sh              # 老的一键流程（采集+测速，不含网关）
├── bin/mihomo          # 内核 (54MB, 自动下载, 不入库)
├── data/
│   ├── private.yaml    # ① 自建节点  ← 见 *.example
│   ├── fallback.yaml   # ② 免费额度  ← 见 *.example
│   ├── nodes.json      # 本轮采集结果
│   └── pool_history.json  # 历史池（并集，核心）
└── out/                # sub.yaml、sub-base64.txt、report.md
```

## 分层配置

复制模板后编辑，改完网关会自动重载（最多等 30 秒）：

```bash
cp data/private.yaml.example  data/private.yaml    # ① 自建，优先级最高
cp data/fallback.yaml.example data/fallback.yaml   # ② WARP / 你的机场
```

- **① 自建**：只要这里有一个通，就永远不会掉到免费池。没有就留空，不报错。
- **② 免费额度**：Cloudflare WARP、你买的机场。额度明确的才放这儿。
- **③ 免费池**：自动采集，无需配置。

两层都留空也能跑，此时总出口就是单级的「③ 免费池」。

## 历史池：为什么不会一夜清空

这是比测速更重要的设计。免费节点的实测存活率只有 2~3%，某天全军覆没很正常。
如果每轮直接覆盖，池子就会归零。

`pool_history.json` 的做法：

| 行为 | 结果 |
|---|---|
| 本轮测到 | 刷新数据、`last_ok`、累计命中次数 |
| 本轮没测到 | **原样保留**，靠 `last_ok` 判断是否过期 |
| 采集全挂（0 个） | 一条都不删 |
| 超过 7 天没通过 | 清理 |
| 超过 300 条 | 按分数截断 |

已用模拟数据验证：14 个节点 → 下轮只剩 2 个新节点 → 池子仍是 16 个（老的一个没丢）；
下一轮空结果 → 仍是 16 个。

## 多站点复检：淘汰"假好节点"

这是本项目最关键的一道筛子，加它之前踩过一次坑：

某个节点延迟 **134ms**（全场最低）、下载 0.7MB/s，按理说是最好的。但它打不开
github / youtube —— 只能过 `generate_204`。客户端用 `url-test` 按延迟选，就正好选中它，
导入后表现为"能上网但很多站打不开"。

所以测速最后一步会拿 3 个站点复核每个入选节点：

| 站点 | 作用 |
|---|---|
| `gstatic.com/generate_204` | 基础连通（标准探测点） |
| `github.com` | 真实大站，能暴露 SNI/路由级阻断 |
| `cloudflare.com/cdn-cgi/trace` | 走另一条骨干，避免同路由误判 |

**至少通 2 个才收录**。实测效果：12 个候选 → 那 2 个假好节点被剔除 → 10 个全部 3/3 通过。

两个相关设计：

- **默认组用 `url-test`，按序降级保留为备选**。早先用的是 `fallback`（按列表顺序取
  第一个能通的），因为 `url-test` 会挑中"134ms 却打不开 github"的假好节点。但假好节点
  现在在入库前就被上面的大站复检剔掉了，进不到组里 —— 所以换成 `url-test` 是安全的：
  由客户端在你当前网络上实测选最快，而不是由云端（美国机房）的排序替你做决定。
  想回到按序降级，在客户端里切到「③ 免费池」即可，成员完全一样。
- **防抖**：`tolerance: 100` —— 延迟差不到 100ms 就不切换，避免两个节点数值抖动时
  客户端反复重建连接。
- **排序把复检通过数放在评分之前**。3/3 的永远排在 1/3 前面。

复检走 `/proxies/{name}/delay` 接口而不是切 `POOL`，所以不影响当前选中，可以并发跑——
12 个节点 3 站只要 18 秒。

不想要这一步就加 `--no-verify`。

## 订阅端点
| 路径 | 用途 |
|---|---|
| `/sub/clash?token=` | Clash / mihomo / Stash，`url-test` 自动择优 + `fallback` 按序降级 |
| `/sub/base64?token=` | v2rayN / Shadowrocket / v2rayNG |
| `/status?token=` | JSON 状态（池子规模、构建时间） |
| `/reload?token=` | 手动重建 |

token 首次启动自动生成，存在 `data/gateway.json`。只监听 `127.0.0.1` 时可用 `--no-token` 关掉。
手机要用就让网关监听局域网：`python3 gateway.py --host 0.0.0.0`（此时**必须**保留 token）。

## 运维命令

```bash
./install.sh --status        # 两个服务的状态 + 端口 + 最近日志
./install.sh --refresh-now   # 不等 04:00，立刻刷一次
./install.sh --uninstall     # 全卸载（数据保留）
tail -f logs/refresh-$(date +%Y%m%d).log
```

## 常用参数

| 参数 | 默认 | 说明 |
|------|------|------|
| `collect.py --max-age` | 72 | 只采最近 N 小时的 TG 帖子。**调小能显著减少无效节点** |
| `probe.py --delay-limit` | 2500 | 延迟准入阈值(ms)，超时淘汰 |
| `probe.py --max-speed` | 100 | 最多多少个节点进带宽测试（每个 8 秒，决定总耗时） |
| `probe.py --keep` | 30 | 单轮保留数量 |
| `probe.py --verify-min` | 2 | 多站点复检至少通过几站 |
| `probe.py --no-verify` | — | 关掉多站点复检（不建议） |
| `gateway.py --port` | 8899 | 网关端口 |
| `gateway.py --no-keepalive` | — | 关掉后台 TCP 保活扫描（默认每 10 分钟扫前 200 个） |

## 实测基线（2026-11-11）

| 采集去重 | 存活 | 存活率 | 平均带宽 | 最快 |
|---------|------|--------|---------|------|
| 558 | 12 | 2.2% | 1.28 MB/s | 1.95 MB/s |
| 559 | 14 | 2.5% | 1.04 MB/s | 1.42 MB/s |

**免费节点就是这个量级。** 同一天跑两次结果只有 40% 重合 —— 节点在被持续消耗。
源不变的话，唯一有效手段是加源和加频率。

## 加自己的源

编辑 `collect.py` 顶部：

```python
TG_CHANNELS = ["oneclickvpnkeys", ...]   # 不带 @
RAW_SOURCES = [("名字", "订阅URL"), ...]  # 支持 base64 / 明文 / clash yaml
```

订阅里套着二级订阅会自动展开一层。

## 判断某个节点值不值得用

```bash
python3 attribute.py
```

1. **垃圾地址** —— 回环/内网（如 `127.0.0.53`，别人泄露的本地配置），直接丢
2. **扩散广度** —— 被几个公开源同时收录。实测 72% 出现在 2 个以上源，聚合仓互相抄，
   "多找源"≠"更多独立节点"
3. **归属聚合** —— 按 /24 聚类。某网段挤十几个节点，大概率同一家批量小号，跑路就全灭

## 风险

免费节点的运营者能看到你的全部流量，**可以做 TLS 中间人**。
只用来临时查资料，绝对不要登录网银、邮箱、公司内网。
境内未经许可自建/使用跨境代理存在合规风险，建议只在自己的开发环境里做连通性研究。

真要长期稳定，**自建一台 ¥10~15/月 的 VPS 才是经济解** —— 放进 `data/private.yaml` 就行，
架构不用改。
